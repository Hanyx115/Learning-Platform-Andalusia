27. IMPORTANT DATA MODELING DECISIONS
==================================================

Follow these principles unless there is a documented reason not to:

- Roles & Permissions are many-to-many.
- Course Details initially support offline-course fields such as schedule, location, and instructor.
- Keep the schema extendable for online/hybrid types later without a destructive redesign.
- Progress should be trackable at a meaningful course/session/lesson level based on the actual Phase 1 learning model.
- Attendance should be associated with the relevant CourseSession where appropriate.
- Courses should normally use soft delete instead of hard delete when historical records depend on them.
- Programs should normally use soft delete instead of hard delete when historical records depend on them.
- Enrollments should preserve history; do not casually hard-delete them.
- Payment and enrollment status-changing operations should have audit/correlation/idempotency information where appropriate.
- Historical payment/progress/attendance records must remain valid even if a course/program becomes inactive.

Never sacrifice historical integrity for convenience.

37. DATABASE QUERY PERFORMANCE AND JOINS
==================================================

Be especially careful about EF Core query performance.

Prefer database-side:
- filtering,
- joining,
- projection,
- sorting,
- grouping,
- aggregation,
- pagination

when that is the correct and efficient approach.

IMPORTANT:
Do not interpret "use joins" as "manually call Join() everywhere."

Use the query form that produces correct, efficient SQL and remains maintainable.

Valid approaches include:
- navigation-property projection,
- Join(),
- Select(),
- SelectMany(),
- GroupJoin(),
- Include() when full related entities are genuinely required.

Do NOT blindly use Include() everywhere.

Do NOT blindly use Join() everywhere.

For read APIs, prefer projection directly into DTOs when possible.

Example concept:

Course
JOIN Category
JOIN Instructor

may be projected directly into CourseSummaryDto rather than loading fully tracked Course, Category, and Instructor entities.

Whenever a significant relational query is implemented:
- explain the approximate SQL operation EF Core will produce,
- explain why the query is efficient,
- identify useful indexes,
- verify authorization is applied before exposing data.

Prefer one well-designed database query over repeated application-side database round trips when practical.

83. GIT SAFETY RULES
==================================================

Never recommend destructive Git operations casually.

Do not:
- force-push main,
- force-push develop,
- reset --hard without a clear warning and explicit reason,
- delete shared branches without checking,
- rewrite shared history casually,
- rebase a branch another developer is actively using without coordination.

Prefer safe collaboration.

Before risky Git operations:
- explain what the command does,
- explain what could be lost,
- give a safer alternative if one exists.

Never commit secrets.

Ensure .gitignore excludes appropriate items such as:
- bin/
- obj/
- node_modules/
- .env files containing secrets
- local secret files
- IDE-specific temporary files
- generated local artifacts not meant for source control

Do not commit .NET User Secrets.

Do not commit real:
- JWT keys,
- database passwords,
- payment keys,
- SMS/email credentials,
- Azure secrets.

Prefer explicit git add paths when useful instead of blindly using git add . if there is a risk of including unrelated files/secrets.
